## Цель и результат

Реализованы загрузка, создание, редактирование, смена статуса и удаление задач.
Данные получаются с готового сервера. Форма и список связаны с API через отдельные функции.
Логика прошла проверки Node.js. Работа страницы в браузере ещё требует проверки на компьютере пользователя.

## Запуск

Из корня проекта:

```bash
cd practice-06
npm start
```

Открыть http://127.0.0.1:5506/ в браузере. API работает на http://127.0.0.1:5505/api.
Одна команда запускает оба сервера; остановка — Ctrl+C. Установка пакетов не нужна.
Если порты заняты: `node tools/start.mjs 5515 5516`, затем открыть
http://127.0.0.1:5516/?api=http://127.0.0.1:5515/api.
Готовая браузерная проверка рассчитана на стандартный порт API 5505.

В терминале из practice-06:

```bash
npm test
npm run check:own
```

Проверки сами создают отдельный API. Для проверки страницы при работающем npm start открыть
http://127.0.0.1:5506/checks.html. Проверки страницы сбрасывают учебные задачи.

## Устройство программы

| Файл | Что делает |
|---|---|
| api-client.js | Отправляет GET, POST, PATCH, DELETE; проверяет HTTP-ответ и JSON |
| task-api.js | Получает и изменяет задачи, проверяет поля ответа |
| form-validation.js | Проверяет название, приоритет и категорию |
| task-view.js | Создаёт карточки и кнопки |
| app-controller.js | Хранит текущие фильтры и связывает действия с запросами |
| dom-app.js | Готовые обработчики формы и кнопок, работа с элементами страницы |
| main.js | Собирает модули и запускает начальную загрузку |
| variant.js | Хранит номер и фильтры варианта |

HTTP-клиент взят из решения ПР5 и расширен методами изменения. Тело превращается в JSON,
добавляется Content-Type. У GET тело запрещено. Ответ 204 возвращает null, другие успешные ответы проверяются и разбираются.
Ошибки HTTP, сети, формата, тайм-аута и отмены различаются по kind.

Форма удаляет пробелы по краям названия и превращает номер категории в число. Название должно содержать 1–100 символов,
приоритет выбирается из трёх значений, категория должна существовать в загруженном списке.
Ошибки выводятся рядом с полями. Сервер также проверяет данные.

## Загрузка и действия

| Состояние | Когда показывается |
|---|---|
| loading | Запрос выполняется |
| ready | Получены задачи |
| empty | Запрос выполнен, но задач нет |
| error | Запрос закончился ошибкой, доступен повтор |

После ошибки первой загрузки повтор снова получает и задачи, и категории.
Если категории уже загружены, повтор запрашивает только задачи.

При создании сервер назначает id и начальный статус. При редактировании отправляются только поля формы,
поэтому completed не сбрасывается. При смене статуса отправляется только completed.
После любого успешного изменения выполняется новый GET с текущими фильтрами.
На время изменения кнопки блокируются. Дополнительно контроллер игнорирует повторную отправку,
пока предыдущая не закончилась. finally снимает блокировку и при успехе, и при ошибке.

## Защита от старого ответа

Перед новой загрузкой предыдущий запрос отменяется через AbortController.
Каждой загрузке даётся очередной номер. Ответ применяется только тогда, когда его номер совпадает с последним.
Поэтому старый ответ не заменит новый список, даже если источник данных не отреагировал на отмену.
Обычная отмена при смене фильтра не показывается как ошибка.

Название и категория вставляются через textContent: строка с HTML остаётся текстом.
Карточки заменяются через replaceChildren. Кнопки доступны с клавиатуры, сообщения и ошибки связаны с элементами формы.
localStorage не используется. После обновления страницы данные запрашиваются заново с API.
При перезапуске процесса API восстанавливается исходный набор из 12 задач.

## Ответы для защиты

1. **Почему fetch не падает на 404?** Сервер прислал ответ. Проверить его статус должен клиент.
2. **Порядок проверки ответа?** response.ok, затем 204, затем Content-Type и JSON.
3. **POST и PATCH?** POST создаёт задачу, PATCH изменяет указанные поля существующей.
4. **201 и Location?** Задача создана; Location указывает её адрес.
5. **Почему 204 не разбирается как JSON?** У него нет тела.
6. **Что такое CORS preflight?** Браузер заранее отправляет OPTIONS, чтобы узнать, разрешены ли метод и заголовки.
   no-cors не помогает читать JSON: ответ становится недоступен коду.
7. **empty и error?** В первом случае ответ успешен, но записей нет. Во втором получить данные не удалось.
8. **Почему без localStorage?** Источник задач теперь сервер.
9. **Зачем GET после изменения?** Чтобы получить подтверждённый список с текущими фильтрами.
10. **Как возникает гонка запросов?** Старый запрос может завершиться после нового.
11. **Почему одной отмены мало?** Ответ мог уже прийти или источник мог не обработать сигнал. Дополнительно проверяется номер запроса.
12. **Почему отмена не показывается как ошибка?** При смене фильтра она ожидаема и не требует действий пользователя.
13. **Кто проверяет форму?** Клиент помогает исправить ввод, сервер повторно проверяет данные перед изменением.
14. **Зачем передавать view?** Можно проверять логику без браузера, подставив объект с нужными методами.
15. **Зачем textContent?** Чтобы название показывалось текстом и не выполнялось как HTML.
